# MUT-03 arithmetic evaluator — initial contract

`poko_mute_evaluator` is a C++20 static library linked to the MUT-02 parser and MUT-01 lexer. Call `parse_arithmetic(source)` first, then `evaluate_arithmetic(ast, options)`. It returns either a typed `NumericValue` or `EvalDiagnostic`. Lex and parse errors remain distinct and are returned by the parser. The evaluator walks the flat postorder AST iteratively and never borrows the source text. It evaluates one expression only; no VM, statements, language locals or hostcalls are implemented. Host-provided numeric bindings are optional and read-only.

## Numeric rules for this baseline

- Supported literal types are `i8/i16/i32/i64`, `u8/u16/u32/u64`, `f32/f64`. Unsuffixed integer literals default to `i32`, or infer the one explicitly suffixed integer type used in the expression. Unsuffixed floats are `f64`. All explicitly typed numeric leaves must agree, and integers never implicitly convert to floats. Identifiers resolve only against explicitly provided numeric bindings, or return `unknown_identifier`.
- Integer `+ - * / %` and unary `+ -` are checked against the selected width; overflow is an error. Unsigned unary minus is rejected. Division truncates toward zero and remainder follows the dividend's sign. Integer and float division by zero is an error. The signed minimum divided or remaindered by `-1` reports overflow. A literal equal to the negative signed minimum is permitted only when it is directly negated (parentheses are allowed); positive out-of-range literals are rejected. These details are initial choices where the broader language spec is not explicit.
- Float `+ - * / %` and unary `+ -` use f32/f64 operations. `%` uses `std::fmod` (truncated quotient, sign of dividend, including signed zero); a zero divisor reports `divide_by_zero`. Cross-platform determinism is not asserted. Nonfinite literal conversion or arithmetic result is rejected; a decimal literal that the host conversion reports out of range, including underflow to zero, is rejected. Arithmetic underflow follows the checked host IEEE environment. Signed zero is preserved. Float overflow/error behavior is provisional until the language's full numeric semantics are settled.
- A default cap of 1,000,000 AST nodes is enforced before evaluation; `EvalOptions::max_nodes` can lower or raise it. It is a node-count limit, **not** the future VM's instruction or heap budget. Lexing and parsing default to a 1 MiB source-byte cap (configurable through `LexOptions`), checked before validation or allocation. This bounds input size but does not impose a total heap or CPU quota; callers must select suitable limits and isolate untrusted workloads.

## Host numeric bindings

Pass a `std::span<const NumericBinding>` as the third argument to `evaluate_arithmetic`. Names are exact, case-sensitive UTF-8 byte strings and are borrowed only during the call. Names must be nonempty and unique; duplicates or empty names produce `invalid_binding` at the root. At most 10,000 bindings and 1 MiB of binding-name bytes are accepted by default; `EvalOptions` can change these limits. A referenced binding must have a recognized type, the matching variant alternative, a value within that integer width, or a finite float. Invalid referenced values return `invalid_binding` at that identifier. Unreferenced values are not validated. Bindings participate in the same type inference and no-implicit-conversion rules as literals. The caller must keep the span, names and values alive and unchanged throughout evaluation. This is not a language declaration, local-variable scope, or a substitute for MUT-06.

## Floating-point safeguards and limitations

The evaluator target disables fast math and contraction and requests strict rounding on supported GCC/Clang/MSVC builds; unknown compilers leave floating evaluation disabled. Floating evaluation saves the caller's floating environment, masks arithmetic traps, checks round-to-nearest-even and subnormal behavior, and restores the environment afterward. If setup, environment checks or normal-path restoration fail, it reports `unsupported_float_environment`; restoration is also attempted during exception unwinding. Integer evaluation does not change the floating environment. A restoration failure cannot guarantee that a broken host environment was restored.

These safeguards and local bit-pattern tests are not a proof of cross-platform deterministic floating point or decimal-conversion equivalence. Windows x64, Android arm64 and hosted replay gates remain unverified. Unsupported platforms/modes must not silently be treated as deterministic.

## Errors and cost

`invalid_binding`, `unknown_identifier`, `type_mismatch`, `literal_out_of_range`, `arithmetic_overflow`, `divide_by_zero`, `invalid_unary`, `unsupported_operator`, `unsupported_float_environment`, `budget_exceeded` and `invalid_ast` are distinct typed errors with original-source positions. Type selection/name checks occur before evaluation; subsequent errors follow the iterative node walk. An invalid/moved-from AST is rejected. Binding lookup sorts names then uses binary search; long or common-prefix names also affect comparison cost. Memory and CPU depend on source, AST, and bindings; allocation failures can propagate as C++ exceptions.
