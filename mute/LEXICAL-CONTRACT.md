# MUT-01 lexical contract, initial implementation

This document records the concrete contract chosen for the first lexer where the broader Mute specification leaves details open. It is an implementation baseline, not a claim that every future language feature is specified. Changing it may require updating downstream parser tests and token goldens. See `../docs/plan/04-mute.md` for the language design.

## Input and positions

- By default, input larger than 1,048,576 bytes is rejected before scanning or allocating as `source_too_large` at byte 0, line 1, column 1. `LexOptions::max_source_bytes` changes this cap; a zero cap permits only empty input. The parser forwards the same option. This is not a total memory limit.
- Within the source limit, the whole source is validated as UTF-8 before lexing; an initial UTF-8 BOM is an error. An invalid sequence is reported at its lead byte, so malformed UTF-8 anywhere takes precedence over lexical errors elsewhere. U+FEFF in string contents is data, not an initial BOM.
- Offsets are byte indices into the *original* source, with end offsets exclusive. They do not depend on the source's lifetime. Lines and columns are 1-based, with columns counting Unicode scalar values; tabs count as one column. CRLF is one newline; bare CR and LF are each one newline. No in-place source rewriting or display-width calculation occurs.
- Only ASCII space, tab, CR and LF are whitespace. Ordinary `//` and non-nesting `/* ... */` comments are skipped. `///` (including `////`) is a doc-comment token through the end of its line. A block comment ends at its first `*/`.

## Tokens

- Identifiers use Unicode 15.1 `XID_Start XID_Continue*`. As specified, `_` by itself is not a valid start, although it is valid after a start character. Keywords are case-sensitive and comprise exactly: `package version allow import as struct enum let var fn async await for in if while loop match guard else break continue return true false move pub spawn trait impl`. Other words, including attribute names and scalar type names, are identifiers.
- Integers are decimal or have a `0x`/`0X`, `0b`/`0B`, or `0o`/`0O` prefix; each prefix must be followed by at least one base-appropriate digit. Optional integer suffixes are `i8 i16 i32 i64 u8 u16 u32 u64`. Floats are decimal with at least one digit on both sides of the dot and optional `f32`/`f64`; `1.` is an integer followed by punctuation. Exponents, digit separators and undotted floats are not supported in this baseline. A following identifier-continuation character that does not form an allowed suffix produces `invalid_number`. No value conversion, range check, or numeric default is performed by the lexer.
- Punctuation: `( ) [ ] { } . , : ; @`. Operators: `<<= >>= ..= == != <= >= && || << >> += -= *= /= %= &= |= ^= .. -> => :: + - * / % ! < > = & | ^ ?`. Operators use longest match; `/` starts a comment when followed by `/` or `*`. Consequently, adjacent generic closing angles can appear as a `>>` token; a future parser must account for that context.
- Strings are single raw tokens including their quotes. In string text, `\\`, `\"`, `\n`, `\r`, `\t`, `\0`, `\{`, and `\}` are recognized escapes; any other backslash escape is an error. Unescaped physical newlines in string text are rejected. An unescaped `{` begins an interpolation whose braces, nested strings and comments are balanced iteratively; an unescaped `}` in ordinary string text remains raw text. Interpolation expressions are not tokenized, validated, compiled, or evaluated here. Physical newlines may occur inside interpolation expressions. No multiline string or Unicode escape syntax is assumed.
- An `end` token always closes a successful stream. Failure instead returns one typed diagnostic and no token stream. Diagnostics identify the start of an invalid number, escape, or unterminated block comment; an unterminated string points to the physical newline or EOF, and an unterminated interpolation to EOF. An unexpected character points to that character.

The implementation uses a C++20 `std::variant` result rather than C++23 `std::expected`, and token offsets rather than stored source views. Allocation failures may propagate as standard C++ exceptions.
